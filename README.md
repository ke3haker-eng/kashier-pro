# كاشير الدكان — الإصدار 2.3

نظام نقاط بيع وإدارة سوبر ماركت متكامل، يعمل كتطبيق ويب (PWA) قابل للتثبيت على الموبايل والتابلت والكمبيوتر، **بلا اعتمادات خارجية وبلا خطوات بناء**: HTML + CSS + JavaScript فقط، والبيانات تُحفظ افتراضياً في **IndexedDB** داخل جهازك (تعمل دون إنترنت)، ويمكنك اختيارياً تحويلها إلى **قاعدة Supabase** لتعمل عدة أجهزة على نفس البيانات (انظر القسم 5).

هذه النسخة ترقية للتطبيق الأصلي (`index.html` + `manifest.json` + `sw.js`) **مع الحفاظ على كل وظائفه** (مسح الباركود بالكاميرا، المنتجات الموزونة بالجرام، البحث، سجل المبيعات، النسخ الاحتياطي، المظهر الفاتح/الداكن، الاهتزاز والصوت، إغلاق الكاميرا بعد كل مسح) وتحويل بياناتها القديمة تلقائياً.

---

## 1) التشغيل السريع

> ملفات التطبيق وحدات ES (`type="module"`)، فلا تعمل بالنقر المزدوج على `index.html` (بروتوكول `file://`). يلزم تقديمها عبر خادم ويب.

**أ) الخادم المرفق (موصى به — يخدم التطبيق ويوفّر النسخ الاحتياطي السحابي الاختياري)**
```bash
node server/server.mjs          # يحتاج Node 18 أو أحدث، ولا يحتاج npm install
# ثم افتح:  http://localhost:8787
```
عند أول تشغيل يُطبع «مفتاح الوصول» للنسخ الاحتياطي ويُحفظ في `data/key.txt`.

**ب) أي استضافة ملفات ساكنة** (Nginx، Apache، GitHub Pages، Netlify، Cloudflare Pages…): ارفع محتويات المجلد كما هي. لا حاجة لأي إعداد.

**ج) تجربة محلية سريعة:** `python3 -m http.server 8080` ثم `http://localhost:8080`.

### التثبيت كتطبيق
- **الكاميرا والتثبيت كتطبيق يتطلبان HTTPS** (ما عدا `localhost`). للوصول من هاتف في نفس الشبكة استخدم أحد الخيارين:
  - خادم الملفات المرفق مع شهادة: `KASHIER_CERT=cert.pem KASHIER_KEYFILE=key.pem node server/server.mjs`
  - أو وكيل عكسي يتولى HTTPS مثل Caddy: `caddy reverse-proxy --from your-domain.com --to localhost:8787`
- **أندرويد/كروم:** قائمة ⋮ ← «تثبيت التطبيق» (أو زر التثبيت في الإعدادات ← النظام).
- **آيفون/سفاري:** مشاركة ← «إضافة إلى الشاشة الرئيسية».
- **الكمبيوتر (كروم/إيدج):** أيقونة التثبيت في شريط العنوان.

## 2) الانتقال من التطبيق القديم دون فقدان بياناتك

> **نصيحة مهمة: لا تستبدل ملفاتك الحالية قبل اختبار النسخة الجديدة.** احتفظ بنسخة من الملفات الأصلية (`index.html`, `manifest.json`, `sw.js`) كما هي.

الطريقة الآمنة (موصى بها):
1. **في التطبيق القديم**: صدّر نسخة احتياطية من زر النسخ الاحتياطي (ملف `.json`) واحفظها.
2. شغّل النسخة الجديدة على **عنوان مستقل أولاً** (مثل `localhost:8787` أو مجلد/نطاق فرعي للتجربة).
3. من **الإعدادات ← النسخ الاحتياطي ← استيراد** اختر الملف القديم — النظام يقبل صيغة التطبيق القديم (`{P,H,T}`) ويعرض معاينة وتحققاً قبل الاستيراد.
4. راجع المنتجات والمبيعات القديمة. وإذا أعجبتك النتيجة انقل الملفات إلى العنوان الفعلي.

الطريقة المباشرة: إذا نشرتَ النسخة الجديدة **على نفس العنوان (نفس الأصل origin)** الذي يعمل عليه التطبيق القديم فإن بياناته في `localStorage` (`sh_p`, `sh_c`, `sh_s`, `sh_t`) **تُرحَّل تلقائياً عند أول فتح**:
- تُحفظ نسخة خام من البيانات القديمة داخل قاعدة التطبيق قبل أي تحويل؛
- **لا تُحذف المفاتيح القديمة أبداً** (يمكنك الرجوع للنسخة القديمة متى أردت)؛
- المنتجات ذات الباركود المكرر لا تُفقد بقية الأصناف بسببها؛
- المبيعات القديمة تظهر في الفواتير بعلامة «قديمة» وبلا تكلفة (لأن التطبيق القديم لم يسجّل تكلفة الشراء) فلا تُحسب لها أرباح وهمية؛
- لا يتكرر الترحيل مرتين.

وإن أردت ملفاً بالبيانات الأصلية القديمة فاستخدم **الإعدادات ← النظام ← تنزيل نسخة البيانات القديمة** (بصيغة التطبيق القديم).

### ملاحظات صريحة عن بعض الميزات
- **الدخول بـ PIN قفل تشغيلي، وليس أمناً حقيقياً.** في الوضع المحلي كل البيانات داخل متصفح الجهاز، فمن يملك الجهاز وأدوات المطوّر يستطيع تجاوزه. فائدته: فصل ما يراه الكاشير عن المدير ومعرفة من نفّذ كل عملية. في الوضع السحابي يضاف حساب Supabase بدور مالك/موظف **يُفرض على الخادم**، لكن تفاصيل الصلاحيات (23) تبقى قفلاً داخل التطبيق.
- **الدفع بالبطاقة/المحفظة تسجيل فقط**: التطبيق يسجّل أن الدفع تم بهذه الطريقة، ولا يتصل بجهاز POS بنكي أو بوابة دفع.
- **الطباعة عبر طباعة المتصفح** (`window.print` مع `@page` للمقاس المختار). لا يرسل أوامر ESC/POS مباشرة للطابعة.

## 5) الوضع السحابي (Supabase) ونشر GitHub

للتطبيق **وضعان للتخزين** تختار بينهما من الإعدادات ← «السحابة (Supabase)»:

| | الوضع المحلي (الافتراضي) | الوضع السحابي (Supabase) |
|---|---|---|
| أين البيانات؟ | داخل متصفح الجهاز | قاعدة PostgreSQL في مشروعك على Supabase |
| عدة أجهزة بنفس البيانات | لا | **نعم** (تصل التغييرات خلال ثوانٍ) |
| بدون إنترنت | يعمل كاملاً | يقرأ فقط؛ **البيع والتعديل يتوقفان** حتى يعود الاتصال |
| الحسابات | قفل PIN تشغيلي | حساب (بريد + كلمة مرور) بدور مالك/موظف على الخادم + PIN |
| الإعداد | لا شيء | مشروع Supabase مجاني + تنفيذ `supabase/schema.sql` |

- **الشرح خطوة بخطوة (بالعربية، لغير المبرمجين):** [`docs/SUPABASE.md`](docs/SUPABASE.md) · [`docs/GITHUB.md`](docs/GITHUB.md)
- **التحويل لا يمسّ بياناتك المحلية:** تبقى على الجهاز، ويمكنك رفعها إلى السحابة بزر، والرجوع للمحلي في أي وقت.
- **أمان:** الجداول مقفلة بالكامل؛ الوصول فقط عبر دوال تتحقق من تسجيل الدخول وعضوية المتجر، وكل متجر معزول عن غيره. المفتاح العام (`anon/publishable`) يظهر لكل من يفتح الموقع وهذا طبيعي؛ **ممنوع وضع `service_role`/`secret`** (التطبيق يرفضه).
- **التعارض:** عند تعديل جهازين لنفس السجل تُحفظ عملية واحدة والأخرى تُعاد على الأحدث؛ بيع آخر قطعة من جهازين معاً لا ينجح إلا مرة واحدة؛ ولا تتكرر العملية إن ضاعت الاستجابة بعد وصولها للخادم.
- **النشر على GitHub Pages:** يأتي المشروع بملف نشر جاهز (`.github/workflows/pages.yml`)؛ كل رفع إلى `main` يُنشَر تلقائياً على رابط `https` مجاني (الكاميرا والتثبيت يعملان). **بيانات المتجر لا تُرفع إلى GitHub أبداً.**
- **حدود صريحة:** (1) لم أجرّبه على مشروع Supabase حقيقي لأنني لا أصل لحسابك — اختُبر على PostgreSQL 16 حقيقي وبجهازين حقيقيين عبر بوابة محاكاة لواجهات Supabase؛ أول تجربة حقيقية ستكون منك. (2) المزامنة بالاستطلاع كل ~4 ثوانٍ وليست اتصالاً لحظياً مفتوحاً. (3) الصلاحيات على الخادم مستويان (مالك/موظف)؛ صلاحيات الأدوار التفصيلية تبقى قفلاً داخل التطبيق. (4) النسخ الاحتياطي اليومي التلقائي في Supabase غير مضمون في الخطة المجانية — صدّر نسخة من التطبيق بانتظام.

## 5-ب) المتجر الإلكتروني للمشترين + الجوال وحجم الخط

- **المتجر الإلكتروني (`store.html`):** واجهة منفصلة لزبائنك: يتصفحون المنتجات كمتجر عادي، يرسلون طلباً، يرفقون **صورة إشعار الدفع**، ويتحدثون معك بمحادثة. لا يرون التكلفة ولا الإدارة، ولا يُحمَّل عندهم أي كود إداري. تصلك الطلبات في صفحة **الطلبات والمحادثات** (تأكيد، تجهيز، تسليم، **إرسال إلى نقطة البيع** كفاتورة معلّقة). يحتاج **الوضع السحابي**. الدليل الكامل بحدوده: [`docs/STORE.md`](docs/STORE.md).
- **باركود المتجر (QR)** ثابت لرابطك وقابل للتنزيل، و**وضع ليلي/نهاري** يبدّله المشتري، و**تنبيهات الطلبات** (جرس + شارة حمراء + شريط الرئيسية)، و**تفريغ المحادثات** يدوياً لتوفير مساحة Supabase. التفاصيل في [`docs/STORE.md`](docs/STORE.md).
- **الجوال:** أُعيد تصميمه ليكون أصغر وأبسط: نقطة البيع تعرض 3 منتجات في الصف، بطاقات الجداول مضغوطة، وأزرار الصفحات الثانوية تُجمع في زر «⋯».
- **حجم الخط والواجهة:** من القائمة ← «المزيد» (أو زر Aa في الشريط العلوي، أو الإعدادات ← المظهر): **حجم الخط** (80–150%) و**حجم الواجهة** (75–140%) و**الكثافة** (تلقائي/مضغوطة/عادية/مريحة). تُحفظ **لكل جهاز** ولا تتزامن.

## 6) النسخ الاحتياطي بخادم خاص (اختياري، بديل أبسط) — وما يحتاج إعداداً منك

التطبيق **لا يرفع أي بيانات لأي مكان** ما لم تُفعّل ذلك بنفسك. لا توجد مزامنة سحابية جاهزة بدون خادم؛ لذلك جهّزتُ لك خادماً مرجعياً:

1. على جهاز/سيرفر دائم التشغيل: `node server/server.mjs`
   | متغير | الوصف | الافتراضي |
   |---|---|---|
   | `PORT` / `HOST` | المنفذ / العنوان | `8787` / `0.0.0.0` |
   | `KASHIER_KEY` | مفتاح الوصول (يُولَّد ويُحفظ في `data/key.txt` إن لم يُحدَّد) | — |
   | `KASHIER_DATA` | مجلد حفظ النسخ | `./data` |
   | `KASHIER_KEEP` | عدد النسخ المحتفَظ بها | `30` |
   | `KASHIER_MAX_MB` | أقصى حجم للنسخة | `200` |
   | `KASHIER_CERT` + `KASHIER_KEYFILE` | تشغيل HTTPS مباشرة | — |
   | `KASHIER_NO_STATIC=1` | واجهة API فقط دون تقديم التطبيق | — |
2. في التطبيق: **الإعدادات ← الخادم**: ضع عنوان الخادم والمفتاح ← «اختبار الاتصال» ← فعّل الرفع التلقائي أو اضغط «رفع نسخة الآن». ومن نفس الشاشة «استعادة» نسخة من الخادم على جهاز آخر.
3. إذا كان التطبيق مفتوحاً من **HTTPS** والخادم **HTTP** سيمنع المتصفح الطلب — اجعل الاثنين HTTPS.

**ما الذي يعنيه هذا وما لا يعنيه:** هو **نسخ احتياطي واستعادة لنسخة كاملة** مع مفتاح وصول وتقييد المحاولات. هو **ليس مزامنة لحظية** بين عدة أجهزة وليس قاعدة بيانات مركزية: لو باع جهازان معاً سيكون لكل منهما بياناته، والاستعادة تستبدل بيانات الجهاز بالنسخة. مفتاح الخادم لا يُكتب في ملفات النسخ ولا يُستبدل عند الاستعادة.

مخطط البيانات وصيغة الملفات وواجهة الخادم: [`docs/SCHEMA.md`](docs/SCHEMA.md).

## 8) تحديث التطبيق لاحقاً

1. عدّل الملفات، ثم شغّل: `node scripts/build.mjs 2.3.1` (يرفع رقم الإصدار في `package.json` و`src/version.js` و`sw.js` ويولّد قائمة الكاش المسبق). **على GitHub Pages لا حاجة لذلك:** ملف النشر الجاهز يفعله تلقائياً بإصدار جديد عند كل رفع.
2. انشر الملفات. عند فتح التطبيق يثبّت المتصفح الإصدار الجديد ويحذف كاش القديم؛ **بياناتك في IndexedDB لا تتأثر** (مُختبَر). زر «التحقق من وجود تحديث» في الإعدادات ← النظام يفرض فحص التحديث (و«مسح كاش التطبيق» لا يمسّ بياناتك).
3. خذ نسخة احتياطية قبل أي تحديث كبير كعادة جيدة.

> `sw.js` المرفق يحوي القائمة المولَّدة فعلاً. بعد تعديل أي ملف في `src/` أو `css/` أعد تشغيل `node scripts/build.mjs`.

### حدود الاختبار (بصراحة)
أُجريت الاختبارات على **Chrome بلا واجهة (headless)** على Linux. **لم تُجرَّب** على: **مشروع Supabase حقيقي** (الاختبار السحابي على بوابة محاكاة فوق PostgreSQL حقيقي)، كاميرا حقيقية، قارئ باركود USB/بلوتوث (حاكيتُه بإدخال لوحة المفاتيح + Enter كما يفعل القارئ)، طابعة حرارية حقيقية (تحققتُ من محتوى حاوية الطباعة و`@page` لا من الورق الخارج)، آيفون/سفاري، أندرويد. لذلك **قبل الاعتماد في المحل**: جرّب مسح باركودات حقيقية، واطبع فاتورة على طابعتك، وافتح التطبيق على هاتفك، ثم اعتمده — ولا تحذف النسخة القديمة قبل ذلك.
